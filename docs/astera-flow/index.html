Filosofia & Interface Universal

Filosofia

O Astera não depende de um único modelo de IA. Toda inteligência especializada deve existir como módulos independentes. O Google ADK apenas decide:

  • qual módulo executar
  • em qual ordem
  • com quais dados

Os módulos nunca conhecem uns aos outros. Toda comunicação acontece através do Runtime.

Interface Universal

Todo módulo deverá implementar a mesma interface lógica. Isso permite substituir qualquer implementação sem alterar o restante do sistema.

initialize()
execute()
health()
metadata()
shutdown()
Organização

Cada módulo representa uma capacidade cognitiva.

Nesta etapa ainda NÃO escolhemos os projetos Open Source.

Primeiro definimos as capacidades.

Depois escolheremos a melhor implementação para cada uma.

Próxima Etapa & Princípio Arquitetural

Próxima Etapa

Após a definição das capacidades cognitivas será criado um novo documento: Astera Open Source Catalog. Esse documento responderá:

  • Qual projeto Open Source implementa cada módulo?
  • Por que ele foi escolhido?
  • Como ele será integrado ao Google ADK?
  • Qual sua licença?
  • Como poderá ser substituído futuramente?

Princípio Arquitetural

O Astera nunca dependerá de um projeto específico. Ele dependerá apenas das capacidades cognitivas.

Projetos Open Source poderão ser substituídos ao longo da evolução da plataforma sem impacto na arquitetura do Runtime.

🧠 Medical Knowledge Layer

Origem da Inteligência Clínica

Objetivo

Esta aba representa a camada de conhecimento médico da plataforma Astera.

Diferente dos Cognitive Modules, que processam informações, ou dos Open Source AI Modules, que executam capacidades especializadas, esta camada representa a origem do conhecimento utilizado durante o raciocínio clínico.

O Astera não toma decisões apenas utilizando modelos de linguagem.

O Astera fundamenta seu raciocínio em bases oficiais, literatura científica, terminologias padronizadas e protocolos institucionais.

Filosofia

Modelos de IA não possuem conhecimento oficial.

Eles apenas raciocinam sobre o contexto recebido.

O conhecimento utilizado pelo Astera deve possuir origem conhecida, rastreabilidade e versionamento.

Toda resposta clínica deverá poder ser relacionada às fontes que fundamentaram sua construção.

Fontes de Conhecimento
Oficial Brasileiro
Ministério da Saúde, SUS, CONITEC, ANVISA, CFM, ANS, PCDT, Diretrizes Terapêuticas.
Internacional
WHO, ICD-11, SNOMED CT, LOINC, RxNorm, HL7 FHIR, NICE, CDC.
Literatura Científica
PubMed, SciELO, Cochrane, Guidelines, Ensaios Clínicos.
Protocolos Institucionais
Fluxos Assistenciais, Diretrizes Internas, Checklists, Templates.
Conhecimento Profissional
Preferências, Especialidade, Atalhos, Modelos de Documento.
Conhecimento Paciente
Histórico, Evoluções, Exames, Medicamentos, Alergias, Timeline.
Pipeline de Processamento & Recuperação

Knowledge Processing

Fonte → Parser → Normalização → Metadados → Chunk → Embeddings → Versionamento → Validação → Indexação → Knowledge Store

Knowledge Retrieval

Pergunta → Retriever → Filtros → Ranking → Reranker → Contexto → Google ADK → LLM

Rastreabilidade

Resposta → Guideline → PubMed → PCDT → Consulta Anterior → Paciente
Integração & Arquitetura

Os Cognitive Modules nunca acessam diretamente as bases, garantindo total desacoplamento. Eles solicitam conhecimento ao Knowledge Service.

Evidence Module → Knowledge Service → Medical Knowledge Layer → Knowledge Retrieval → Resposta

O modelo de linguagem e os Open Source AI Modules não executam conhecimento. A Medical Knowledge Layer fornece conhecimento; os módulos executam capacidades. O modelo recebe apenas o contexto preparado pelo Runtime.

🏗️ Infrastructure Architecture

Componentes Físicos da Plataforma

Objetivo

Esta visualização representa toda a infraestrutura física oficial da plataforma Astera.

Aqui documentamos onde o Astera executa, os bancos de dados utilizados, como ocorre a comunicação entre os componentes e a fundação técnica da plataforma.

Infrastructure & Orchestration
Kubernetes Cluster
Orquestração de todos os serviços da plataforma. Hospeda o Runtime, Gateway e agentes cognitivos. Escalabilidade automática baseada em carga.
Astera Runtime (Pods)
Serviços escaláveis que executam o núcleo da plataforma e a API Layer para clientes externos e Desktop.
NATS (Event Bus)
Mensageria de altíssima performance para comunicação assíncrona entre módulos, agentes e o Runtime.
Persistência & Dados
PostgreSQL (Relacional)
Banco de dados principal. Armazena dados transacionais, sessões, contexto clínico de pacientes e configurações globais.
Qdrant / pgvector
Banco de dados vetorial para Retrieval (RAG) corporativo, busca de guidelines médicas e memória semântica.
Redis / Valkey
Gerenciamento de estado de curto prazo, caching ultra-rápido, rate limiting e locks distribuídos para agentes.
S3 / MinIO (Object Storage)
Armazenamento escalável de arquivos de áudio, imagens médicas (DICOM), laudos PDF e artefatos de IA.
Cognitivo & Integrações
Google ADK (Agent Runner)
Workers dedicados para execução de pipelines cognitivos, agentes autônomos e orquestração de raciocínio.
LLM Gateway (LiteLLM)
Proxy unificado para comunicação com modelos fundacionais externos (Gemini, Claude, GPT).
FHIR Gateway
Interface padronizada (HL7 FHIR) para troca de dados com sistemas hospitalares e EMRs legados.
Operação, Deploy & Suporte
Observability Stack
OpenTelemetry, Grafana e Prometheus para monitoramento de métricas, logs estruturados e tracing distribuído.
Auth Gateway (Keycloak)
Gerenciamento de identidades, Single Sign-On (SSO) e segurança de acesso à plataforma.
GitOps (ArgoCD)
Pipeline de Continuous Deployment (CD) gerenciando infraestrutura como código diretamente do repositório Git.

☁️ Cloud Strategy

Decisão Arquitetural (ADR) da Plataforma

Objetivo

Este documento define oficialmente a estratégia de infraestrutura da plataforma Astera.

Ele estabelece como a plataforma será implantada, quais tecnologias fazem parte da infraestrutura oficial e quais princípios deverão ser seguidos durante toda a evolução do projeto.

Este documento representa uma decisão arquitetural (ADR) da plataforma.

Visão & Princípio Fundamental

Visão

O Astera é uma plataforma Cloud First.

Toda a inteligência da plataforma será executada na infraestrutura da Astera Cloud.

O Desktop é apenas a experiência do usuário.

Toda computação acontece na nuvem.

Princípio Fundamental

O Astera deve ser independente do provedor de nuvem.

A plataforma poderá ser hospedada inicialmente na AWS.

Entretanto, o Runtime nunca poderá depender de serviços proprietários específicos quando existir uma alternativa Open Source madura.

A arquitetura deve permanecer portável.

Filosofia & Estratégia

Filosofia

O usuário nunca deve saber:

  • onde a plataforma está rodando;
  • qual servidor está sendo utilizado;
  • qual GPU executou a IA;
  • qual LLM respondeu;
  • qual projeto Open Source foi utilizado;
  • qual provedor de infraestrutura está hospedando o sistema.

Toda essa responsabilidade pertence exclusivamente ao Astera.

Estratégia

A AWS será utilizada como infraestrutura. Não como plataforma proprietária.

Isso significa que utilizaremos a infraestrutura da AWS sempre que fizer sentido, mantendo o núcleo do Astera completamente desacoplado.

Desenvolvimento Local & AWS

Serviços AWS

Os serviços da AWS deverão ser utilizados apenas quando agregarem valor operacional claro (Ex: Amazon S3, AWS Secrets Manager, Amazon EKS).

O uso de serviços altamente acoplados deverá ser evitado (Ex: Lambda, DynamoDB, EventBridge, Cognito, Step Functions). Só poderão ser adotados após análise arquitetural.

Ambiente Local Oficial

O ambiente local deve reproduzir a infraestrutura de produção. Toda a plataforma deverá subir utilizando Docker Compose.

Docker Compose
↓
Astera Runtime → PostgreSQL → Redis → Qdrant → NATS → MinIO → Grafana → Langfuse → Mailpit

LocalStack será utilizado apenas para desenvolvimento (simular S3, Secrets Manager, IAM). Nunca faz parte da arquitetura de produção.

Princípios Arquiteturais & Benefícios
☁️ Cloud First Toda inteligência executa na Astera Cloud.
🔌 Cloud Agnostic O Runtime nunca depende diretamente de um provedor específico.
🏗️ Infrastructure as Code Toda infraestrutura deverá ser reproduzível.
📦 Container First Todos os serviços oficiais deverão possuir imagens Docker.
⚡ Event Driven Toda comunicação interna utiliza NATS.
🔓 Open Source First Sempre priorizar soluções Open Source maduras. Serviços proprietários só com grande vantagem.

Benefícios

  • Baixo acoplamento e redução de vendor lock-in.
  • Facilidade de migração entre provedores e evolução tecnológica contínua.
  • Melhor previsibilidade operacional.
  • Ambiente local semelhante ao ambiente de produção.
  • Atualizações transparentes para o usuário.

Objetivo Final

O Astera deve oferecer uma infraestrutura moderna, escalável e preparada para crescimento, mantendo total independência arquitetural.

A AWS será a primeira infraestrutura oficial. Entretanto, a arquitetura permanecerá portável, desacoplada e preparada para executar em qualquer ambiente compatível com containers e Kubernetes, garantindo longevidade e evolução sem comprometer seu núcleo.

🏛️ Architecture Decisions (ADR)

Painel de Controle da Arquitetura

Objetivo

Esta aba representa o conjunto oficial de decisões arquiteturais da plataforma Astera.

Cada item listado nesta página foi analisado, discutido e aprovado durante o processo de arquitetura da plataforma.

Essas decisões formam a base técnica do Astera e somente poderão ser alteradas através de uma nova Architecture Decision Record (ADR).

O objetivo desta aba é evitar rediscussões, garantir consistência arquitetural e acelerar a evolução da plataforma.

Architecture Version

Princípios da Plataforma
Cloud First & Agnostic
Toda a inteligência roda na Astera Cloud. A plataforma é projetada para ser Cloud Agnostic, sem lock-in em serviços proprietários, rodando via Kubernetes.
Open Source by Design
Sempre que houver uma alternativa open source madura, ela deve ser priorizada. Modelos cognitivos são implementados via projetos open source desacoplados.
Decoupled AI
O Runtime do Astera (Google ADK) é totalmente independente dos modelos de fundação. LLMs e ferramentas são intercambiáveis via interfaces comuns.
Privacy & Security First
Arquitetura multi-tenant robusta. Dados de pacientes (PII) podem ser anonimizados e a plataforma deve suportar ambientes on-premise isolados se necessário.
Event-Driven Architecture
A comunicação assíncrona entre módulos cognitivos e serviços da plataforma ocorre através de mensageria escalável (NATS).
Evidence-Based Generation
Nenhum raciocínio clínico confia exclusivamente na memória paramétrica dos LLMs; todo conhecimento é rastreável e baseado na Medical Knowledge Layer.
